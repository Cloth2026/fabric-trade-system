# 产品需求与已确认规则

## 产品目标

第一版服务小型面料贸易团队，优先解决以下四项高频工作：

1. 快速查找面料资料。
2. 记录寄样和客户反馈。
3. 制作客户报价单。
4. 管理供应商和采购价格。

当前已优先实现面料档案、供应商和采购数据基础。寄样、客户反馈和客户报价单仍属于后续阶段。

## 面料档案规则

- 面料档案必须围绕结构、生产过程、工艺链、计价单位和资料可补全性设计，不能只记录名称、成分和价格。
- V1 暂时不管理颜色、色号和色卡。
- 面料分为 `knitted` 和 `woven`。计价单位由服务器派生：`knitted -> kg`，`woven -> meter`。
- 面料编号固定以 `SDD-` 开头，总长度不超过 64 字符，并在租户内唯一。
- 基础必填字段是 `code`、`name`、`fabricType`、`developmentSource`、`composition`、`weight`、`width`。
- 允许保存暂不完整的真实资料，但必须计算 `completenessPercent` 并记录 `missingInfoFlags`。
- 坯布、染整、后工艺分别使用 `none`、`pending`、`available` 状态；状态与明细必须一致。
- 用途、季节、认证等保存稳定配置 key，不将中文显示文字当作业务值。

## 多供应商货源与报价

- 一款面料可以关联多个供应商。
- 同一面料与同一供应商当前只保留一条 `FabricSupplier` 长期货源关系。
- 每个货源关系记录供应商货号、供应商样品状态、质量差异、是否首选和备注。
- 采购价、币种、MOQ、交期、联系人和报价日期属于 `FabricSupplierQuote` 报价快照，不放在长期关系上覆盖更新。
- 报价历史不能覆盖；每次有效报价新增一条记录。
- 报价必须有 `purchasePrice`，`quoteDate` 未提供时由服务器生成。
- 每条历史报价必须保留报价当时的 `supplierUnitId`。以后修改货源当前生产单元，不得改写历史报价。
- 最多只能有一个首选货源。新增面料时如果已有供应商但没有明确首选，服务器将第一家设为首选。
- 列表展示的最新采购价来自所选货源按报价日期和创建时间排序后的最新报价。

## 供应商与生产单元

- `Supplier` 表示公司、工厂、档口或贸易主体，不把“一车间、二车间”建成独立供应商。
- 一个供应商可以拥有分厂、事业部、车间、部门、生产线、外协点或其他生产单元。
- 染厂、印花厂可按染色一车间、染色二车间、数码印花部、圆网印花车间等生产单元管理。
- 生产单元可记录业务类型、主要产品、原料范围、工艺能力、限制、默认 MOQ、参考交期、打样能力、负责人和质量风险。
- 生产单元的 `businessTypes` 至少一项，并可多选。
- 生产单元原则上只启用或暂停，不提供业务删除。
- 后续将生产单元关联到面料货源或报价时，必须同时验证当前租户和所属供应商一致。

## 页面与组件规则

- 面料库进入时不默认选中第一款面料，也不自动打开详情。
- 用户点击表格行或卡片后才打开详情。
- 桌面端默认使用专业表格，卡片视图作为辅助浏览。
- 入库批次视图暂缓，直到库存模块进入开发阶段。
- 面料详情是独立只读展示组件，不能用 disabled 表单模拟。
- 面料详情包含“基础资料”“供应商与采购”“工艺与质量”三个标签页。
- 每次打开不同面料时默认进入“基础资料”。
- 面料详情支持遮罩和右上角按钮关闭，关闭动画完成后必须可稳定重开。
- 新增面料保存成功并完成关闭后刷新当前列表。
- 当前详情中的“编辑面料”“添加货源”“新增报价”仍是静态提示，不得让用户误以为已完成写入能力。
- 供应商详情与编辑分离；查看详情不能直接进入编辑状态。
- 面料新增、未来编辑应复用字段分区、配置选项和通用表单控件，但详情保持独立只读展示，不强行复用表单 UI。

## API 与数据边界

- `tenantId` 只能由服务端上下文确定，客户端请求不得提供或覆盖。
- 数据库和 API 保存稳定英文 key；中文标签由 `ConfigOption` 或前端标签映射负责。
- 金额使用 `Decimal`，只读 API 返回字符串。
- 跨租户详情和更新统一按资源不存在处理，避免泄露其他租户数据。
- 新功能不得读取或写入 `Fabric.supplierId`、`Fabric.supplierQuote`、`Fabric.minimumOrderQty` 等 legacy 单供应商字段。
- 重要写操作应与 `OperationLog` 在同一事务中完成。

## 用户、角色、权限、登录与审计日志规则

以下规则已经确认，正式设计见 `docs/DESIGN_AUTHORIZATION_AND_LOGIN.md`。**当前代码尚未实现**，系统与界面仍处于临时单租户上下文。

### 账号与登录

- 认证使用 Better Auth，不自行实现密码哈希和 Session；会话为 PostgreSQL 数据库 Session。
- V1 使用邮箱 + 密码登录；现有 `username` 只作为内部账号编码与搜索字段，不作为登录凭证。
- 不开放公开注册；用户只能由 owner 或 admin 创建。
- 初始密码由服务器安全随机生成，**只向管理员显示一次**，不写入 seed、Git、migration 或日志。
- 新用户首次登录必须修改初始密码；未修改前只能访问查询会话、退出和修改密码三个接口。
- 管理员重置密码后生成新临时密码、置为必须改密，并撤销该用户全部旧 Session。
- 用户停用后立即不能登录并撤销全部 Session；历史记录保留。
- 登录失败不区分账号不存在与密码错误，文案统一；连续失败会暂时锁定。
- 不使用 `AUTH_ENABLED` 或任何本地免登录开关作为正式运行方案。

### 租户、角色与权限

- 一个用户只属于一个 Tenant；`tenantId` 由已验证 Session 和用户关系确定，客户端不能提交或覆盖。
- 一个用户可以拥有多个角色，权限取所有角色权限的并集。
- V1 使用六个固定角色：`owner`、`admin`、`sales`、`purchasing`、`merchandiser`、`viewer`；不允许新增、删除或自定义角色。
- 权限字典与固定角色矩阵由服务端代码常量维护，不使用 `ConfigOption`，不提供数据库权限编辑器。
- 权限 key 使用稳定英文点号格式（如 `purchase_price.view`、`user.assign_roles`），中文只在展示层映射。
- 一个 Tenant 可以有多个 owner，但必须始终保留至少一个启用状态的 owner；最后一个启用的 owner 不能被停用、移除 owner 角色或降级，该保护必须在服务端事务内保证，不能只靠前端判断。
- admin 不能新增、编辑、停用或分配 owner 身份。
- 无 `purchase_price.view` 权限时，服务端不返回采购价格字段（采购报价金额、工艺单价、报价与订单的成本与毛利），不能只在前端隐藏。
- 未登录返回 401；已登录但无权限返回 403；跨租户访问具体资源返回 404。
- 不能只完成登录页面就宣称权限系统完成；现有全部业务 API 完成服务端授权前，系统不得对公网开放。

### 操作日志

- 操作日志只允许查看，不允许编辑或删除。
- 日志分类为登录安全、用户权限、业务操作三类，并记录成功/失败、请求 ID、IP、设备与操作人快照。
- 登录失败且账号无法识别时 `userId` 为空，只记录脱敏登录标识。
- 日志不得记录密码、密码摘要、Session Token、完整 Cookie 或完整认证请求。

### 暂不做

公开注册、SSO、OAuth、MFA、组织架构、审批流、行级"只能看自己数据"、自定义角色、日志清理任务。

## 范围状态

### 已真实实现

- 新增面料保存、真实列表、搜索筛选分页、真实详情和新增后刷新。
- 多供应商货源与报价历史数据模型。
- 供应商和生产单元的真实 API 与 UI。
- 面料和供应商读取的租户隔离及请求竞态保护。

### 已设计但未开发

- 用户认证、固定角色权限与审计日志（`docs/DESIGN_AUTHORIZATION_AND_LOGIN.md`，待数据模型实施）。
- 面料货源独立新增和维护。
- 采购报价独立新增和首选货源调整。
- 面料编辑。
- 寄样和客户反馈。
- 客户报价单。

### 暂缓

- 颜色、色号和色卡。
- 入库批次 UI 和完整库存。
- 大型权限系统和复杂审批流。
